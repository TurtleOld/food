# htmx для серверных взаимодействий, Alpine для эфемерного UI, без JSON-слоя

Уточняет ADR-0002 и отменяет запланированный в нём JSON-слой (`django-modern-rest`, OpenAPI). Сервер отвечает только HTML: полными страницами или фрагментами для htmx. Всё, что читает или меняет данные, идёт через htmx, и сервер остаётся единственным источником правды. Alpine.js хранит только эфемерное UI-состояние, которое не переживает перезагрузку (открыт ли bottom sheet, активная вкладка, камера сканера). Alpine не делает `fetch` и не рендерит данные из JSON. Даже живой пересчёт КБЖУ при вводе количества — это htmx-запрос с debounce, а не расчёт на клиенте: формула снапшота (ADR-0001) живёт в одном месте. JSON-слой вернётся, только когда появится потребитель, которому нужен не HTML.

## Considered Options

- **JSON-эндпоинты + Alpine рендерит данные** (исходный план ADR-0002) — отвергнут: дублирует сериализацию и валидацию, а потребителя, которому нужен не HTML, нет.
- **JSON точечно (например, ответ прокси Open Food Facts)** — отвергнут: прокси тоже отдаёт фрагмент, то есть предзаполненную форму Продукта.
- **Только HTML через htmx** — выбран.

## Consequences

- Базовый CRUD (записи, продукты, цель) работает обычными формами POST → redirect и без JS; htmx его только улучшает. Сканер и bottom sheet доступны только с JS.
- Без `hx-boost`: только точечные `hx-get`/`hx-post` с явным target.
- Без morph (idiomorph): Alpine-острова не кладём внутрь заменяемых target, либо их состояние законно сбрасывается вместе с фрагментом.
- Один URL — одна сущность: CBV отдаёт полную страницу или фрагмент по заголовку `HX-Request`, сервер ставит `Vary: HX-Request`, service worker не кэширует запросы с `HX-Request`. `htmx.config.historyCacheSize = 0`; `hx-push-url` — только там, где фрагмент меняет адрес экрана.
- CSRF: `hx-headers='{"X-CSRFToken": "{{ csrf_token }}"}'` на `<body>`.
- htmx и Alpine вендорятся с закреплёнными версиями в `static/vendor/`, без CDN.
- Фрагмент — встроенный `{% partialdef %}` (Django 6) внутри страницы-владельца; CBV-миксин выбирает фрагмент при `request.htmx`, `Vary: HX-Request` ставит общая middleware на все ответы. `id` target совпадает с именем partial.
- Успешный POST из шторки отвечает фрагментом ленты, тост — OOB-swap из Django `messages`, шторку закрывает `HX-Trigger`. Невалидная форма — 200 с ошибками.
- Потеря сессии на htmx-запросе — `HX-Redirect` на вход, а не 302, который htmx вставил бы в target.
