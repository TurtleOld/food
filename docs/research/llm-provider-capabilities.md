# Возможности провайдеров LLM: DeepSeek, vision и инструменты

Дата исследования: 2026-10-13. Источники — официальная документация провайдеров, проверенная в этот день. Цены и модели DeepSeek за последние два месяца менялись трижды, перед реализацией страницу цен стоит перепроверить.

## Вывод

**Изображения принимает сам DeepSeek, так что весь Ассистент можно держать на одном провайдере.** Модель `deepseek-flash` (DeepSeek-V4.1-Flash, вышла 2026-09-10) через OpenAI-совместимый `/chat/completions` принимает текст и картинки, вызывает инструменты (tool calls, есть strict-режим) и отдаёт JSON. Типичное фото этикетки с ответом стоит примерно $0.001–0.003. Семья из 4 человек при активном использовании уложится в **единицы долларов в месяц**. Отдельный vision-провайдер и OCR не нужны.

Рекомендуемая комбинация:

- Текст, фото и инструменты идут через `deepseek-flash`. Модель и `base_url` задаются в настройках, как и решено в карте.
- Штрихкод распознаёт клиент: в приложении уже стоит `BarcodeDetector`-полифилл, `static/js/scanner.js`. LLM читает цифры под штрихкодом только как запасной путь, и прочитанное проверяется по контрольной цифре EAN.
- OCR (Tesseract или облачный) не нужен.
- Резерв: Gemini Flash-Lite через его OpenAI-совместимый эндпоинт. Но Россия не входит в список стран, где доступны Gemini API и OpenAI API (см. ниже), поэтому как резерв он годится только при подходящем расположении сервера и биллинга.

### Изображения (Vision) [4]

- Картинки передаются стандартным OpenAI-блоком `{"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,..."}}`, а также по внешнему URL или через `file_id` из Files API. Files API бесплатен [5].
- Форматы: JPEG, PNG, GIF, WebP. Формат определяется по содержимому файла.
- Токены: картинка масштабируется примерно до 1300×1300 пикселей по площади (маленькие увеличиваются примерно до 544×544). **Верхняя граница — 1024 токена на изображение**, так что фото с телефона в любом разрешении стоит не больше 1024 токенов. `detail: "low"` сжимает картинку до 512×512: дешевле, но для мелкого текста таблицы КБЖУ это, скорее всего, вредно.
- Лимиты: тело запроса до 48 MiB, одно изображение до 32 MiB (через `file_id` до 64 MiB), до 8192 px по стороне, до 600 изображений в запросе.
- **Ограничение, важное для дизайна:** изображения разрешены только в сообщениях `user`. В `system` и `assistant` они дают 400. Поэтому фото должно приходить в ход Ассистента как пользовательское сообщение, а не как результат инструмента.
- Анонс multimodal (2026-08-21) обещал до 384 токенов на картинку [5]. Действующий гайд называет потолок 1024 [4]. В расчётах ниже взят 1024.

### Инструменты и структурированный вывод

- **Tool calls** работают в формате OpenAI (`tools`, `tool_calls`, сообщения `role: "tool"`), в режиме с рассуждением и без него [6].
- **Strict-режим (Beta):** нужны `base_url=https://api.deepseek.com/beta` и `strict: true` у каждой функции. Сервер проверяет JSON Schema. В схемах объектов все свойства должны быть `required`, плюс `additionalProperties: false`. Не поддерживаются `minLength`/`maxLength`/`minItems`/`maxItems` [6]. Для Предложений (Продукт с КБЖУ) этого хватает.
- Вставлять в историю tool calls, которых модель не генерировала, Chat Completions не умеет. Это поддерживают Anthropic-эндпоинт и Responses API [6]. Наш Ассистент получает данные инструментами в рамках хода, так что ограничение нас не касается.
- **JSON Output:** включается через `response_format={"type": "json_object"}`. В промпте должно быть слово «json» и пример. Документация предупреждает, что API «иногда может вернуть пустой content» [7]. Значит, нужна обработка пустого ответа и повтор. Для структурированных данных надёжнее strict tool call, чем `json_object`.

### Режим рассуждения [8]

- Рассуждение **включено по умолчанию** (effort `high`). Выключается через `extra_body={"thinking": {"type": "disabled"}}`, глубина задаётся через `reasoning_effort: low|high|max`.
- Токены рассуждения оплачиваются как выход. Для распознавания этикетки и коротких ответов разумно ставить `low` или выключать рассуждение. Это главный рычаг стоимости.
- В режиме рассуждения при наличии `tools` нужно возвращать `reasoning_content` предыдущих ходов обратно в API. Клиенту это надо учесть.
- `temperature` в режиме рассуждения игнорируется.

### Кэширование контекста [9]

- Включено всегда, на диске, код менять не нужно. Попадание в кэш дешевле промаха в 50 раз ($0.006 против $0.30 в пик).
- Кэшируются префиксы на границах запросов: конец ввода и конец вывода. Общий префикс разных запросов (системный промпт + описания инструментов) тоже кэшируется после повторов. Работает по принципу best-effort, кэш живёт от часов до дней.
- В `usage` приходят `prompt_cache_hit_tokens` и `prompt_cache_miss_tokens`. По ним удобно считать фактические расходы для месячного лимита.
- Практический вывод: системный промпт и список инструментов держать стабильными и в начале запроса.

### Лимиты [10]

- Ограничена только параллельность: 2500 запросов одновременно на аккаунт для Flash. Лимитов RPM/TPM в документации нет. При превышении приходит HTTP 429.
- Параметр `user_id` (через `extra_body`) изолирует кэш и модерацию по пользователям. Можно передавать id Члена семьи, но не персональные данные.
- Пока ответ генерируется, сервер может слать пустые строки или SSE-комментарии `: keep-alive`. Если запрос не начал выполняться за 10 минут, соединение закрывается.

## Сколько стоит фото и месяц

Оценка по ценам `deepseek-flash` в пиковые часы, то есть сверху.

**Один ход с фото этикетки:** системный промпт и инструменты ~2000 токенов (из кэша), фото ≤1024, текст пользователя ~100, ответ с вызовом инструмента ~300, рассуждение `low` ~500.

- Вход с промахом кэша: ~1124 × $0.30/1M ≈ $0.00034
- Вход из кэша: ~2000 × $0.006/1M ≈ $0.00001
- Выход: ~800 × $1.20/1M ≈ $0.00096
- **Итого ≈ $0.0013.** Со вторым запросом после результата инструмента, где фото уже лежит в кэшированном префиксе, выходит примерно $0.002–0.003. Вне пика вдвое дешевле.

**Месяц для семьи из 4 человек** (с запасом):

| Нагрузка | Объём | Оценка |
|---|---|---|
| Фото | 4 × 5/день × 30 = 600 | ~$1.5–2 |
| Текстовые ходы | 4 × 20/день × 30 = 2400 | ~$2–4 |
| Вечерние и недельные Сводки | ~140 | < $0.5 |
| **Итого** | | **≈ $4–7** |

Если рассуждение включено на `high`, выход растёт в несколько раз, и сумма может дойти примерно до $10–15. Разумный лимит в `.env` — $5–10 при `low` или выключенном рассуждении. Числа объёмов здесь условные. Их стоит сверить с реальными `usage`, когда появится учёт расходов (тикет 09-llm-budget).

|---|---|---|---|---|
| DeepSeek `deepseek-flash` [1][4] | $0.30 / $1.20 (пик) | ≤1024 | $0.001–0.003 | да |
| Google `gemini-3.5-flash-lite` [11][12] | $0.30 / $2.50 | 258 за тайл 768×768, регулируется `media_resolution` | ~$0.001–0.002 | **нет в списке стран** [13] |

- У Gemini есть OpenAI-совместимый эндпоинт `https://generativelanguage.googleapis.com/v1beta/openai/` с `image_url`, `tools` и `response_format` [12]. Бесплатный tier существует, но данные бесплатного tier идут на улучшение продуктов Google [11].
- Russia отсутствует в списках доступных регионов Gemini API [13] и OpenAI API [15], проверено поиском по страницам. Доступность определяется местом сервера и платёжного аккаунта. Для прод-сервера в РФ эти варианты нерабочие.
- Цены OpenAI я взял из таблицы Standard. Поддержку картинок у конкретных nano/luna-моделей на странице цен не проверить, её нужно смотреть в карточке модели.

## OCR вместо vision?

Не стоит.

- **Облачный OCR** (Google Cloud Vision TEXT_DETECTION) стоит $1.50 за 1000 изображений после 1000 бесплатных в месяц [16]. Это ~$0.0015 за фото, столько же или дороже, чем весь vision-вызов DeepSeek. При этом OCR отдаёт только сырой текст, который всё равно придётся разбирать LLM в КБЖУ.
- **Локальный OCR** (Tesseract и подобные) бесплатен. Но таблица КБЖУ на мятой и изогнутой упаковке со смесью кириллицы и латиницы — тяжёлый случай для классического OCR. Добавится системная зависимость в Docker-образ и CPU-нагрузка на сервер, а потом всё равно понадобится LLM для структурирования. Эти оценки качества основаны на общих знаниях, а не на замерах.
- OCR не решает вторую задачу из вопроса: **узнать Продукт по фото без этикетки**. Это умеет только vision.
- Штрихкод не нужно ни OCR-ить, ни отдавать LLM. Его декодирует клиентский сканер, который уже есть.

## Что проверить до спеки

1. **Качество на реальных этикетках.** V4.1-Flash вышла месяц назад, и данных о том, как она читает русские таблицы КБЖУ, у меня нет. Перед фиксацией конвейера фото стоит прогнать 10–20 своих снимков с `detail: auto` и с разными уровнями рассуждения.
2. **Пустые JSON-ответы** [7]. Нужен повтор или переход на strict tool call.
3. **Нестабильность линейки.** За два месяца сменились три модели и имена. Имя модели держать в настройках, а не в коде.
